# MES 设备管理与生产订单管理设计

## 目标

补齐一个可用的基础 MES 设备管理模块，以及一个可完成“订单创建、编辑、下达、开工、完工、取消”闭环的生产订单管理模块。

本次范围聚焦在基础版生产订单，不引入设备派工、报工、工单拆分、工序级执行跟踪等更复杂能力。

## 当前项目现状

- 前端已经完成了产品管理、物料管理、BOM 维护、工序管理、工艺路线管理等基础生产管理模块。
- 前端菜单中已经预留了 `设备管理` 和 `生产订单管理` 入口，但当前没有真正可用的页面与路由接入。
- 后端已经存在 `Device`、`ProductionOrder` 相关的 Entity、DTO、Mapper、Service、Controller，以及初始化测试数据。
- `Device` 模块后端已经具备基础 CRUD、分页、关键字搜索、类型筛选、编码唯一性校验能力。
- `ProductionOrder` 模块后端已经具备基础 CRUD、分页、状态流转接口，但当前列表和详情返回的是主表字段，前端如果直接使用，会只能拿到 `productId`、`routeId` 这类外键，不适合直接做业务页面展示。

## 面向用户的功能设计

### 1. 设备管理

`生产管理 > 设备管理` 作为独立主数据页面存在。

页面支持：

- 分页列表
- 按设备名称或编码关键字搜索
- 按设备类型筛选
- 新增设备
- 编辑设备
- 删除设备
- 展示启用/停用状态

字段沿用当前后端结构：

- `name`：设备名称
- `code`：设备编码
- `type`：设备类型
- `location`：设备位置
- `status`：状态

页面风格复用现有产品管理、物料管理、工序管理的交互模式，保持基础 MES 主数据页的一致体验。

### 2. 生产订单管理

`生产管理 > 生产订单管理` 作为独立业务页面存在。

页面支持：

- 分页列表
- 按订单号关键字搜索
- 按订单状态筛选
- 新增订单
- 编辑订单
- 删除订单
- 执行订单状态流转

订单主表字段以现有后端为主：

- `orderNo`：订单号
- `productId`：产品 ID
- `routeId`：工艺路线 ID
- `quantity`：生产数量
- `planStartDate`：计划开始时间
- `planEndDate`：计划结束时间
- `status`：订单状态

### 3. 生产订单的状态流转

本次生产订单按基础 MES 的最小闭环设计，状态流转如下：

- `未开始` -> `进行中`
- `进行中` -> `已完成`
- `进行中` -> `已取消`

不允许：

- 直接从 `未开始` 跳到 `已完成`
- 已完成后再次修改或重启
- 已取消后再次恢复
- 已进入 `进行中` 后继续编辑主数据

页面上应根据状态动态控制操作按钮：

- `未开始`：允许编辑、删除、开工
- `进行中`：允许完工、取消
- `已完成`：只读
- `已取消`：只读

## 数据与接口设计

### 设备接口

复用现有后端接口：

- `GET /api/device/list`
- `GET /api/device/{id}`
- `POST /api/device`
- `PUT /api/device/{id}`
- `DELETE /api/device/{id}`

前端新增 `deviceApi`，封装形式与当前 `productApi`、`materialApi`、`processApi` 保持一致。

### 生产订单接口

现有后端接口：

- `GET /api/order/list`
- `GET /api/order/{id}`
- `POST /api/order`
- `PUT /api/order/{id}`
- `DELETE /api/order/{id}`
- `PUT /api/order/{id}/start`
- `PUT /api/order/{id}/complete`
- `PUT /api/order/{id}/cancel`

本次重点补强订单列表和详情的展示能力，让接口返回适合前端直接渲染的结构，而不是只返回裸外键。

建议新增展示型返回结构，例如 `ProductionOrderVO`，至少包含：

- `id`
- `orderNo`
- `productId`
- `productName`
- `productCode`
- `routeId`
- `routeName`
- `routeCode`
- `quantity`
- `status`
- `planStartDate`
- `planEndDate`
- `createdAt`
- `updatedAt`

## 后端设计

### 设备模块

设备后端现有能力已经接近可直接使用，本次以后端小改动或不改动为主：

- 保留现有分页查询结构
- 保留关键字搜索与设备类型筛选
- 保留设备编码唯一性校验
- 维持当前 `status` 语义，不额外扩展设备状态机

### 生产订单模块

当前生产订单后端最大的不足，不是状态流转，而是返回结构不适合页面直接展示。

建议改动：

- 新增 `ProductionOrderVO`
- 在查询订单列表和单条订单详情时，联表查询产品与工艺路线
- 返回产品名称、产品编码、路线名称、路线编码
- 保持创建、编辑、删除、开工、完工、取消这些接口路径不变

需要补的基础校验：

- 创建或编辑订单时，产品必须存在
- 创建或编辑订单时，工艺路线必须存在
- `quantity` 必须大于 0
- 计划结束时间不能早于计划开始时间
- 只有 `未开始` 状态允许编辑和删除
- 只有 `未开始` 状态允许开工
- 只有 `进行中` 状态允许完工或取消

本次不扩展：

- 订单与设备绑定
- 订单与具体工序执行记录绑定
- 报工、暂停、复工
- 工单拆单/合单

订单行操作建议包括：

- 编辑
- 删除
- 开工
- 完工
- 取消

前端根据状态控制按钮是否展示，而不是把所有动作一股脑显示出来。

建议交互：

- 对状态变更类操作使用二次确认
- 操作成功后刷新列表并提示
- 编辑弹窗打开时，如果是编辑，先拉取该订单详情回填

## 异常与边界处理

- 订单数量为空、为 0 或小于 0 时，前端先校验，后端再兜底校验
- 计划结束时间早于计划开始时间时，前端直接阻止提交
- 产品或工艺路线已不存在时，后端返回明确错误，前端直接提示
- 用户尝试编辑已开工订单时，后端拦截并返回清晰错误
- 用户连续点击状态按钮时，以后端校验为准，前端负责按钮 loading 和重复点击保护
- 设备编码重复时，后端返回明确错误，前端展示提示
